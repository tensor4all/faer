# Pfaffian #176: removing the permutation wall

## Scope and decision

Follow-up to [#176](https://github.com/tensor4all/faer/issues/176), based on
`caa432340e9213b2b8cbac2dd1362bd7fdac5008` (includes #174).
The maintainer prioritized f64 at n=1024; c64 is regression coverage and n=64
is report-only. Stop at an open PR with green CI; no merge or auto-merge.
This record supersedes the old #171 worklog's statement that phase timings
were unavailable. The previously completed diagnosis is reused, not rerun.

Choose **parallel eager symmetric swaps**, not deferred indexed arithmetic:
keep the existing contiguous SIMD update kernels, pivot order and floating-point
operation order. Delete swaps of columns before the current panel start: that
panel's contribution has already been applied and these scratch-only columns
have no future readers. Split each remaining prefix/mixed-sign/tail segment
independently, so one member does not inherit all strided work. The joined
callback uses disjoint element pointers, not overlapping mutable matrix views;
the corner negation and permutation parity are applied once.

Use SVD's existing 64-byte stride-padding pattern at column-byte strides that
are multiples of 1 KiB, avoiding cache-set aliasing during row access. Scratch
query and allocation share the same row-count helper. The algorithm sees only
n logical rows. This is bounded working storage, not per-call heap allocation.

Immutable `MatRef` cannot be overwritten by an in-place factorization. Copy it
once in parallel on the caller's Team, fusing lower-triangle finite validation
with the copy. Initialize ignored upper/diagonal and extra work rows to zero;
never read the caller's ignored upper/diagonal. Finish all members before
checking the stack atomic flag. Square/even/empty checks remain before scratch
access. Finite validation cannot be hoisted out of calls accepting fresh input.
No API, dependency, executor, numerical algorithm, trailing kernel, tolerance,
ISA default or small-n-specific path was added.

## Candidate rejected and correction

The first complete candidate dispatched every swap on the caller's whole Team.
Its retained f64 n1024 normal API medians were Seq 37.0934 ms / Team8 10.5444 ms,
but n64 Team8 was 0.1424 ms and n128 Team8 0.3292 ms. Padding and deleting dead
prefix work had made many swaps cheaper than dispatch. The complete first run
is retained at `/home/shinaoka/work/pfaffian-ref/176/measure/`; it is not pooled
with the corrected candidate.

The final candidate uses **the existing LU swap rate and Derived region-width
policy**, with `n-start-2` element pairs and one joined section per swap. The
same parallel kernel remains available when its dispatch pays; smaller regions
degenerate to the same callback inline. No new rate, machine constant, tuning
knob or size threshold was introduced. Private tests force the parallel swap
kernel independently of this cost gate.

## Measurement limits and acceptance

Same existing harness/fixtures: three sessions, three warmups and ten retained
calls each, median of three session medians; shares use summed phase time over
all thirty total times, not median shares. Phase 1T uses a real serial Team
token; the normal 1T driver uses Seq. CPU4 / CPU4-11, observer process 533135
pinned to CPU0-3,36-63, L3 topology verified (approved Team8 two-domain exception).
EPYC 7702P, V3/AVX2 runtime, no target-cpu=native; BLAS/OMP/Julia thread counts 1.
Boost off, governor performance; observed 1-minute load 1.09-1.88.

**Ungated shared-host diagnostic, not paired performance-adoption evidence.**
All our builds finished before measurement, but an unrelated cpueinsum build
started during the final run: compiler processes appear in 32/96 cell snapshots
(210 process records); its surviving parent affinity was CPU56-63 after the run.
It was neither stopped nor moved. Every attempt/sample is retained, with no
retry or outlier removal. In particular n64/c64/Team8 contains a 14.193 ms call
(14.075 ms setup), so its aggregate shares are not a stable overhead breakdown.
Do not use that cell or small percentage differences as an adoption claim.

Normal f64 n1024: Seq **37.3221 ms**, Team8 **10.0514 ms**; Seq/Fortran **0.353**,
well inside <=1.05, but **best1T/Team8 = 3.713**, below >=4. Best1T includes the
new faster candidate Seq, not the old 105.82 ms Fortran time. n256 and n512 also
miss 4x. n64/f64 Seq is **0.0370 ms**, Seq/Fortran **1.334**: still a miss and not
a reason to specialize this PR. No general acceptance/adoption claim is made;
#176 remains open for the missing targets.

The f64 n1024 instrumented Team8 call is 11.1093 ms: trailing update d
6.1495 ms (54.51%), serial pending kernel c 1.6270 ms (14.80%), swaps
1.7662 ms (16.02%), setup 0.5333 ms (4.79%), normalization/product e
0.6809 ms (6.21%). Swaps fell from the old 19.47 ms/49.81% wall to 1.77 ms,
but are not free. Outside-d is no longer synonymous with serial work: swaps
and copying can now use the Team. These phase times include clocks and are
not substituted for the uninstrumented 10.0514 ms API median.

No new c64 optimization, n64 fast path, trailing-GEMM replacement, Team32,
AVX-512 execution, upstream control, dedicated-host adoption campaign, GPU,
reference remeasurement, merge, or release was performed.
